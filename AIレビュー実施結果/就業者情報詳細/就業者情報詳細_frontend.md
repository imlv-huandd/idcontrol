# 就業者情報詳細 レビュー結果

## 指摘事項

### 1. 履歴追加・更新が未実装で設計イベントを満たしていない
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「追加ボタン押下」「更新ボタン押下」で、クライアントバリデーション、確認ダイアログ、API連携、完了後リフレッシュが必須。
  - 実装: handleHistoryAdd / handleUpdate が alert("更新機能は準備中です。") のみで、API呼び出し・確認ダイアログ・完了処理が未実装。
- 指摘内容:
  - 履歴追加モード・編集モードの主要機能が動作せず、設計で定義された業務フロー（登録/更新）を実行できない。
- 期待されるテスト:
  - 追加/更新ボタン押下で確認ダイアログが表示されること。
  - 確認OK時にAPIが呼ばれ、成功時にCOM01004表示・詳細表示モードへ戻ること。
  - APIエラー時にコード対応メッセージが表示されること。

### 2. 詳細表示・編集系で追加情報項目定義の取得が行われず、画面項目生成仕様に不一致
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「初期表示（詳細表示モード）」で、就業者情報項目定義を取得して追加情報エリアを生成することが必須。
  - 実装: useEffect内で fetchPersonAttribute を呼ぶのは新規登録モードのみ。詳細表示/履歴追加/編集では personAttributes が未取得のままになり得る。
- 指摘内容:
  - モードによって追加情報エリアの表示が欠落し、設計の「動的項目生成」要件を満たさない可能性が高い。
- 期待されるテスト:
  - 詳細表示初期化時に属性定義APIが呼ばれ、追加情報のラベル・入力欄が表示されること。
  - 履歴追加・編集遷移時も属性定義が維持されること。

### 3. 追加情報バリデーションでフラグ型必須時に実行時例外が発生し得る
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「追加情報入力チェック」で入力タイプごとの妥当性検証が必須。
  - 実装: validate() で FLAG型値を boolean として扱いながら、必須チェックで value.trim() を呼んでおり、boolean.trim is not a function が発生し得る。
- 指摘内容:
  - 特定データ定義（FLAGかつ必須）で登録操作がクラッシュし、入力チェック自体が成立しない。
- 期待されるテスト:
  - FLAG必須=true/false/未設定の各ケースで例外なく検証できること。
  - FLAG必須違反時に想定メッセージが表示されること。

### 4. テナント就業者IDが非新規モードで常時非活性となっており、編集仕様と整合しない
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「履歴編集ボタン押下」で参照表示項目を編集可能に切り替えること、更新時に重複チェック(更新)の対象にテナント就業者IDを含むことが記載。
  - 実装: tenantPersonId 入力欄は modalMode !== create で常時 disabled。
- 指摘内容:
  - 編集モードでもテナント就業者IDを変更できず、設計上想定される更新入力範囲と乖離している可能性がある。
- 期待されるテスト:
  - 編集モード遷移時にテナント就業者IDの活性/非活性が設計通りであること。
  - テナント就業者ID変更時の重複エラー表示を確認できること。

### 5. 履歴一覧のソート・重複表示ロジックが設計定義と不一致
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の項目定義No.13で「有効開始日の降順」「重複期間チェックに基づく赤字表示」が必須。
  - 実装: 履歴表示は endDate 降順でソート。赤字判定は endDate 一致のみで、期間重複判定ではない。
- 指摘内容:
  - 画面上の履歴順序と警告表示が業務仕様とずれ、利用者が誤った履歴を選択・判断するリスクがある。
- 期待されるテスト:
  - startDate 降順で表示されること。
  - 期間重複あり/なしのデータで赤字表示が仕様通りに切り替わること。

### 6. 「就業者なし」エラー時のメッセージ運用が設計メッセージID準拠になっていない
- 優先度: Low
- 種別: 実装不備
- 対象: frontend/src/pages/workers/WorkerDetail.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「初期表示（詳細表示モード）」で対象なし時はCOM01009表示。
  - 実装: 対象なし時に固定文言 alert('就業者情報が見つかりません。') を表示。
- 指摘内容:
  - メッセージ管理の一貫性が崩れ、文言変更・多言語化・監査観点で保守性が低下する。
- 期待されるテスト:
  - 対象データなしでCOM01009が表示されること。

### 7. 単体テストコード未作成により、設計で重要な分岐と異常系が未担保
- 優先度: High
- 種別: テスト不足
- 対象: 就業者情報詳細（frontend/src/pages/workers/WorkerDetail.jsx）
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の各イベント（初期表示、履歴変更、登録、追加、更新、削除、キャンセル）。
  - 実装: フロントエンドの該当コンポーネントに対するテストコードが存在しない（ユーザー前提とも一致）。
- 指摘内容:
  - 正常系だけでなく、権限制御、未入力、不正入力、API失敗時挙動の品質保証ができない。
- 期待されるテスト:
  - 正常系: 新規登録成功、詳細表示初期化、履歴切替表示。
  - 異常系: API 4xx/5xx、対象データなし、バリデーション違反、削除失敗(COM01010)。
  - 分岐: 権限あり/なしで履歴操作ボタン表示切替。
  - 非更新確認: キャンセル時の破棄確認、変更なし更新抑止（将来実装含む）。

### 8. 追加情報入力タイプ別バリデーションの境界・異常観点が未検証
- 優先度: Middle
- 種別: テスト不足
- 対象: 就業者情報詳細（追加情報バリデーション）
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「追加情報入力チェック内容」。
  - 設計書: spec/050.テスト/テスト観点.md の「入力値バリエーション」「境界値」「異常系」。
  - 実装: InputTypeごとの検証分岐が多数あるが、テスト不在。
- 指摘内容:
  - メール形式、半角数字、存在コード、日付形式、最大桁数などの仕様逸脱が混入しても検知できない。
- 期待されるテスト:
  - 入力タイプ別に有効/無効値を最低1ケースずつ。
  - maxLength の 境界値（上限-1/上限/上限+1）。
  - プルダウンで未定義コード選択時のエラー。

### 9. 設計確認: 詳細初期表示の初期選択レコード要件（有効開始日最大）との整合
- 優先度: Middle
- 種別: 設計確認事項
- 対象: 就業者情報詳細（初期表示ロジック）
- 根拠:
  - 設計書: spec/基本設計/機能設計/060.就業者情報/就業者情報詳細.md の「初期選択は有効開始日が最大のレコード」。
  - 実装: 初期選択が props(startDate/endDate) 依存で決まり、常に startDate 最大とは限らない。
- 指摘内容:
  - 呼び出し元パラメータの契約次第で仕様不一致となるため、仕様として「呼び出し元が最大開始日を保証する」のか「画面側で最大を選ぶ」のか明確化が必要。
- 期待されるテスト:
  - 呼び出し元パラメータが未指定/不一致でも、初期選択が仕様通りになること。

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足:
  - 新規登録成功、詳細表示初期化、履歴変更反映、削除成功後リフレッシュの検証が未整備。
- 入力値バリエーション不足:
  - 基本情報（必須/任意）と追加情報（InputType別）の有効・無効値パターン未網羅。
- 境界値不足:
  - 100文字・2048文字・6文字などの上限境界、日付フォーマット境界のテスト不足。
- 分岐条件不足:
  - モード(create/view/edit/history-add)、権限あり/なし、履歴重複有無の分岐検証が不足。
- データ入出力不足:
  - API呼び出しパラメータ、レスポンス反映、エラーコード別表示の確認不足。
- 非更新確認不足:
  - キャンセル時の変更破棄、変更なし更新、対象外データ不変の検証が不足。
- 異常系不足:
  - 通信失敗、対象データなし、バリデーション違反、権限不足時の表示・遷移確認が不足。

## 総評
- Highの指摘として、履歴追加/更新未実装、追加情報定義取得漏れ、FLAG必須時クラッシュ可能性があり、現状は業務利用前の修正が必須です。
- 画面の主要イベントが設計通りに完結しておらず、機能停止および誤判定リスクが残っています。
- まず実装不備（High）を解消し、次に履歴表示ロジックと編集可否の仕様整合（Middle）を詰める優先順位が妥当です。

## 残留リスク・確認できなかった範囲
- バックエンドAPI（特に updatePerson）の実装完了状況・レスポンス契約の最終版は本レビューでは未確定。
- 画面呼び出し元（WorkerSearch等）とのパラメータ契約（startDate/endDateの保証条件）は設計書上で明示不足のため要確認。

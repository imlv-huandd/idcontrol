# 連携システム画面 レビュー結果

## 指摘事項

### 1. 連携先インターフェイスのマッピング編集遷移が未実装
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の イベント定義 No.9「インターフェイスマッピング編集ボタン押下」で、対象インターフェイスのマッピング画面へ遷移すると定義されている。
  - 実装: frontend/src/pages/integration/IntegrationSystemList.jsx で連携元の「マッピング編集」には onClick がある一方、連携先の「マッピング編集」ボタンには onClick がなく遷移処理が未接続。
- 指摘内容:
  - 連携先インターフェイスのマッピング編集操作が機能せず、設計必須イベントが未実装。
- 期待されるテスト:
  - 連携先インターフェイス行の「マッピング編集」押下で正しい画面に遷移すること。
  - 権限あり時のみ表示され、表示時は遷移可能であること。

### 2. 権限制御がシステム単位要件を満たしていない
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/common/UserAuthority.jsx, frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の 初期表示および項目定義で、「対象システムの連携システム管理者/操作者」に応じた表示制御が要求されている。
  - 実装: frontend/src/common/UserAuthority.jsx の isAuthorityRelationsystemAdmin / isAuthorityRelationsystemUser は権限文字列の全体有無のみを判定し、systemId を受け取る判定が存在しない。frontend/src/pages/integration/IntegrationSystemList.jsx はこの判定で各システム行のボタン表示を制御している。
- 指摘内容:
  - システム単位の権限制御がフロントで担保されず、対象外システムでも操作ボタンが表示される可能性がある。
- 期待されるテスト:
  - システムAのみ権限ありのユーザーで、システムA/B混在一覧時にAのみ編集系ボタン表示となること。
  - テナント管理者、連携システム管理者、連携システム操作者それぞれで表示制御が設計通りであること。

### 3. フロントエンド単体テストが未整備で主要仕様の不具合を検出できない
- 優先度: High
- 種別: テスト不足
- 対象: 連携システム画面機能全体
- 根拠:
  - 設計書: spec/050.テスト/テスト観点.md の 単体テスト観点（正常系、入力値バリエーション、境界値、分岐条件、データ入出力、非更新確認、異常系）で網羅的検証が要求されている。
  - 実装: フロントエンド側で IntegrationSystemList に対応するテストコードが存在せず、tests 配下は relationSystems のバックエンドテスト中心。
- 指摘内容:
  - 画面遷移、権限表示、削除活性制御、API失敗時表示などの重要仕様が自動検証されていない。
- 期待されるテスト:
  - 権限別表示、折り畳み、追加/変更/削除、遷移、API成功/失敗、ダイアログ活性制御の画面単体テスト。

### 4. システム名のクライアント入力チェックが未実装
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の システム編集ダイアログ 保存ボタン押下で、クライアントサイドバリデーション「システム名称入力チェック」を実施すると定義。バリデーション定義で必須・100文字以内。
  - 実装: handleCreateRelationSystemConfirm / handleUpdateRelationSystemConfirm は入力値検証なしで API を実行。
- 指摘内容:
  - 未入力や桁超過をフロントで早期検知できず、設計通りの入力制御になっていない。
- 期待されるテスト:
  - 未入力時に保存不可またはエラー表示となること。
  - 100文字ちょうどは許可、101文字以上はエラーとなること。

### 5. システム編集ダイアログのキャンセル確認が未実装
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の キャンセルボタン押下で、入力変更時は確認ダイアログ COM01008 を表示し、キャンセル時は処理中断と定義。
  - 実装: キャンセルボタンは setShowSystemModal(false) のみで閉じており、変更有無判定と確認ダイアログ表示がない。
- 指摘内容:
  - 編集途中の入力が確認なしで破棄され、設計仕様と不一致。
- 期待されるテスト:
  - 未変更時は即時クローズ、変更時は確認ダイアログ表示、ダイアログキャンセル時は入力保持で閉じないこと。

### 6. エラー状態の表示経路が不明確で運用時の原因把握が難しい
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の 各イベントでエラー時メッセージ表示が前提。
  - 実装: error state は更新されるが JSX 上で error を直接表示しない。AlertMessage は alert state を表示する作りだが alert はこの画面で設定されていない。
- 指摘内容:
  - 例外発生時の表示経路が統一されておらず、失敗ケースで利用者への案内が漏れるリスクがある。
- 期待されるテスト:
  - 一覧取得失敗、登録失敗、更新失敗、削除失敗でユーザーにエラーメッセージが必ず表示されること。

### 7. 並び順の責務がAPI依存で画面仕様とのトレースが弱い
- 優先度: Low
- 種別: 設計確認事項
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/090.連携システム/連携システム.md の 連携システムエリアで、システムID昇順・連携元→連携先→インターフェイスID昇順の表示順を要求。
  - 実装: 取得データをそのまま表示し、フロント側で並び替え処理は実装していない。
- 指摘内容:
  - 表示順保証をどこで担保するかが画面実装上で明確でない。API保証前提なら設計上の責務分担を明文化すべき。
- 期待されるテスト:
  - APIが仕様順で返却した場合に表示が保持されること。
  - 仕様外順で返却された場合の扱い（API側保証か画面側補正か）を決め、決定に沿ったテストを追加すること。

### 8. 未使用state/importが残存し保守性を下げている
- 優先度: Low
- 種別: 実装不備
- 対象: frontend/src/pages/integration/IntegrationSystemList.jsx

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足:
  - 初期表示成功時に、システム一覧・折り畳み初期状態・権限別ボタン表示が仕様通りである検証が不足。
  - システム追加/変更/削除成功時に完了メッセージ表示と一覧再取得が行われる検証が不足。
- 入力値バリエーション不足:
  - システム名未入力、空白のみ、通常値、重複相当値の入力パターン検証が不足。
- 境界値不足:
  - システム名100文字許容、101文字拒否の境界テストが不足。
- 分岐条件不足:
  - テナント管理者/連携システム管理者/連携システム操作者/権限なしでの表示分岐検証が不足。
  - deleteTarget が system/interfaceUpper/interfaceLower の分岐ごとの削除API呼び出し検証が不足。
- データ入出力不足:
  - 各API呼び出しでパラメータ（systemId/interfaceId/times）とHTTPメソッドが正しいことの検証が不足。
  - 画面遷移先URL生成の検証（特に連携先マッピング編集）が不足。
- 非更新確認不足:
  - 削除チェック未ON時に削除不可であること、キャンセル時にAPI未実行であることの検証が不足。
  - 変更なしキャンセル時に保存処理が走らないことの検証が不足。
- 異常系不足:
  - 一覧取得失敗、保存失敗、削除失敗、競合（times不整合）時の表示と画面状態復帰の検証が不足。

## 総評
- High指摘として、連携先マッピング編集の未実装とシステム単位権限制御不足は、機能欠落および認可観点の不整合に該当し、リリース前の修正が必要。
- 併せて、フロントエンド単体テスト未整備により、今回のような仕様差分を継続的に検出できない状態。
- 修正優先順位は、1) 未実装遷移 2) 権限制御 3) テスト基盤整備 4) 入力チェック・キャンセル確認の順が妥当。

## 残留リスク・確認できなかった範囲
- spec/詳細設計 に画面詳細仕様（UI責務や並び順責務分担）を明示したドキュメントが見当たらず、並び順保証の責務（API側かフロント側か）を断定できない。
- spec/レビュー観点 配下に実体ドキュメントがなく、設計レビュー用の組織標準チェックリストとの照合は未実施。
- 特になし

# ユーザー検索 レビュー結果

## 指摘事項

### 1. 自分自身削除チェックが固定値で実装されており、仕様どおりの判定になっていない
- 優先度: High
- 種別: 実装不備
- 対象: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx)
- 根拠:
  - 設計書: [spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md](spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md) のバリデーション定義「削除対象ユーザーIDがログインユーザーIDと異なること（USR01001）」
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) で `user.userId === 14` の固定値比較を実施
- 指摘内容:
  - ログイン中ユーザーとの比較ではなく固定ID判定のため、実ユーザーに対して誤判定が発生する。
  - 他ユーザーであっても削除不可になる、または自分自身が削除可能になる不整合が起こり得る。
- 期待されるテスト:
  - ログインユーザーIDと削除対象IDが一致する場合に削除不可（USR01001相当）になること。
  - ログインユーザーIDと削除対象IDが不一致の場合に確認ダイアログへ進むこと。

### 2. 削除処理が設計の同時更新制御要件（タイムスタンプ条件）を満たしていない
- 優先度: High
- 種別: 実装不備
- 対象: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx)
- 根拠:
  - 設計書: [spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md](spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md) の削除条件「ユーザーID + 検索時タイムスタンプ」、削除失敗時COM01010
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) のDELETE送信でタイムスタンプを含めず、行データをそのまま送信
- 指摘内容:
  - 楽観ロック用のタイムスタンプ連携がないため、同時更新・先行削除との競合を正しく検知できない。
  - 設計で要求される「先に更新された場合の制御（COM01010）」の成立根拠が欠落している。
- 期待されるテスト:
  - 検索時取得のタイムスタンプをDELETE要求に含めること。
  - サーバーが競合を返した際に競合メッセージを表示し、一覧状態が壊れないこと。

### 3. 削除API異常時のエラー処理に不備があり、サーバーメッセージを正しく扱えない
- 優先度: High
- 種別: 実装不備
- 対象: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx)
- 根拠:
  - 設計書: [spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md](spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md) のサーバーサイドバリデーションエラー時メッセージ表示要件
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) で `const errorData = response.json();` としており `await` なし
- 指摘内容:
  - `response.json()` がPromiseのまま扱われるため、`errorData.message` が取得できず、サーバー返却メッセージを表示できない。
  - 仕様上必要なエラーメッセージの精確な表示が担保されない。
- 期待されるテスト:
  - DELETEが4xx/5xxを返した場合、レスポンス本文のメッセージが表示されること。
  - 本文がない場合はフォールバック文言が表示されること。

### 4. 検索失敗時のエラー表示が画面に出ず、障害時の利用者通知要件を満たせない
- 優先度: High
- 種別: 実装不備
- 対象: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx)
- 根拠:
  - 設計書: [spec/050.テスト/テスト観点.md](spec/050.テスト/テスト観点.md) の異常系観点（エラー時の観測可能な結果を確認）
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) で `setError(...)` はあるが、`error` を表示するUIがない
- 指摘内容:
  - 通信失敗時に利用者が失敗理由を確認できないため、再試行や問い合わせの判断が困難になる。
  - 例外発生時の可観測性が不足している。
- 期待されるテスト:
  - 検索API失敗時にエラー文言が画面上へ表示されること。
  - 失敗後に再検索で正常復帰できること。

### 5. 削除完了後の一覧更新が設計どおり「再検索 + ページ補正」になっていない
- 優先度: Middle
- 種別: 実装不備
- 対象: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx)
- 根拠:
  - 設計書: [spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md](spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md) の削除後仕様「現在ページで再検索、該当なし時は最終ページ表示」
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) で `setResults(prev => prev.filter(...))` のみ実施し再検索・ページ補正を未実施
- 指摘内容:
  - クライアント側の単純除外のみでは、サーバー側の実データ件数・ページ数と不整合が生じる。
  - 最終ページへの遷移要件が満たされない可能性がある。
- 期待されるテスト:
  - 削除後に現ページ再検索されること。
  - 削除で当該ページが空になった場合に最終ページへ補正されること。

### 6. 検索結果のメールアドレス昇順要件の実現責務が不明確
- 優先度: Middle
- 種別: 設計確認事項
- 対象: ユーザー検索機能（フロント・API連携）
- 根拠:
  - 設計書: [spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md](spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md) の検索結果仕様「ソート順はメールアドレス昇順」
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) では受信結果をそのまま表示し、フロント側ソートなし
- 指摘内容:
  - ソート責務をAPIで担保する前提であれば設計上明記が必要。現状はフロント実装だけでは順序保証できない。
  - API仕様・実装の保証条件を明文化しないと、将来変更で順序崩れが起きやすい。
- 期待されるテスト:
  - 検索結果が常にメールアドレス昇順で返ることをAPI契約テストで確認する。

### 7. 単体テストコード未作成により、主要仕様の回帰検知ができない
- 優先度: Middle
- 種別: テスト不足
- 対象: ユーザー検索機能全体
- 根拠:
  - 設計書: [spec/050.テスト/テスト観点.md](spec/050.テスト/テスト観点.md) の単体テスト観点（正常系、異常系、境界値、分岐、非更新確認）
  - 実装: [frontend/src/pages/users/UserSearch.jsx](frontend/src/pages/users/UserSearch.jsx) に対応するテストコードが未作成（前提条件）
- 指摘内容:
  - 検索・ページング・削除・遷移・エラー表示の分岐が多いにもかかわらず自動テストで担保されていない。
  - 仕様変更時に破壊的変更を早期検知できない。
- 期待されるテスト:
  - 正常系: 検索成功、0件表示、ページング遷移、編集/新規遷移。
  - 異常系: 検索失敗、削除失敗（バリデーション/通信失敗/競合）。
  - 境界値: 20件/21件、最終ページ削除時、空文字入力、長大入力。
  - 非更新確認: 削除キャンセル時に一覧が変化しないこと。

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足:
  - 検索成功時の一覧表示、0件時メッセージ表示、編集遷移、新規遷移、削除成功後の再検索動作。
- 入力値バリエーション不足:
  - ログインID/ユーザー名/かな/メールの単独指定、複合指定、空文字、前後空白を含む条件。
- 境界値不足:
  - 件数20件（ページャ非表示）と21件（ページャ表示）の境界。
  - 最終ページ1件を削除した際のページ補正。
- 分岐条件不足:
  - 自分自身削除判定、一致/不一致。
  - 削除確認ダイアログのOK/キャンセル分岐。
  - API正常/異常、レスポンス本文あり/なしの分岐。
- データ入出力不足:
  - 検索クエリのパラメータ組み立て。
  - 削除リクエストに必要項目（ユーザーID、タイムスタンプ）を含める契約。
- 非更新確認不足:
  - 削除キャンセル時、通信失敗時、バリデーションエラー時に一覧・件数が変更されないこと。
- 異常系不足:
  - 検索失敗時のエラー表示。
  - 削除失敗時（権限不足、競合、対象なし、通信エラー）のメッセージ表示。

## 総評
High指摘は、削除判定の誤り、同時更新制御不足、エラーハンドリング不備といった機能正当性に直結する内容です。
特に削除機能は誤削除や競合未検知につながるため、最優先で修正とテスト追加が必要です。
次点で、削除後再検索とテスト未整備を解消し、回帰に強い状態へ引き上げるのが妥当です。

## 残留リスク・確認できなかった範囲
- API側でメールアドレス昇順が常に保証されるかは、本レビューではフロント実装中心のため確証を置けていません。
- メッセージID（COM/USR）の実表示方針が「ID表示」か「文言表示のみ」かの運用ルールは設計書間で最終合意の確認が必要です。

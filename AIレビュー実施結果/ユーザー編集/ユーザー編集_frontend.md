# ユーザー編集 レビュー結果

## 指摘事項

### 1. 戻る時の変更有無判定が常に変更ありになり、仕様の非更新確認を満たせていない
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー編集.md の「戻るボタン押下」では、入力内容が変更されている場合のみ確認ダイアログ(COM01008)を表示する仕様。
  - 実装: frontend/src/pages/users/UserEdit.jsx で `originalForm` は初期化されるが更新されず、`hasChanges()` は `!originalForm` の間、任意入力値があるだけで true を返すため、編集モードで未変更でも確認ダイアログが表示される。
- 指摘内容:
  - 変更検知の基準データが保持されていないため、非更新時に確認ダイアログを出さないという設計要件を満たせていない。
- 期待されるテスト:
  - 編集モードで初期表示直後に戻るを押下した場合、確認ダイアログが表示されず遷移すること。
  - 編集モードで1項目変更後に戻るを押下した場合、確認ダイアログ(COM01008)が表示されること。

### 2. 編集モード初期表示で対象ユーザー不存在時の遷移仕様が未実装
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー編集.md の「画面初期表示（編集モード）」では、ユーザーが存在しない場合はエラーメッセージ(COM01009)を表示してユーザー検索画面へ遷移する仕様。
  - 実装: frontend/src/pages/users/UserEdit.jsx の `fetchUserData` 例外処理で alert 表示のみ行い、遷移処理はコメントアウトされている。
- 指摘内容:
  - 不存在ユーザー時の画面遷移が行われず、設計のエラー時導線と不整合。
- 期待されるテスト:
  - 編集モード初期表示で GET API が 404/NotFound を返した際、COM01009相当のエラー表示後にユーザー検索画面へ遷移すること。

### 3. フロントエンド単体テストが未作成で、単体テスト観点の必須範囲を満たしていない
- 優先度: High
- 種別: テスト不足
- 対象: ユーザー編集機能（frontend/src/pages/users/UserEdit.jsx, frontend/src/utils/validators.js, frontend/src/components/ConfirmDialog.jsx, frontend/src/components/AlertMessage.jsx）
- 根拠:
  - 設計書: spec/050.テスト/テスト観点.md の「単体テスト観点」で正常系、入力値バリエーション、境界値、分岐条件、データ入出力、非更新確認、異常系の観点を要求。
  - 実装: frontend 配下に UserEdit および関連モジュールのテストコード（*.test.js/*.spec.js）が存在しない。
- 指摘内容:
  - 仕様に対する検証資産が無く、主要分岐・異常系・境界値の品質担保ができていない。
- 期待されるテスト:
  - 正常系: 新規登録成功、編集更新成功、戻る遷移。
  - 入力値バリエーション/境界値: 各入力の必須、最大文字数(100/2048)、英数字制約、メール形式。
  - 分岐条件: 新規/編集モード、確認ダイアログ OK/キャンセル、未変更/変更あり戻る。
  - データ入出力: 編集モード初期取得値の画面反映、送信ペイロード内容。
  - 非更新確認: バリデーションエラー時に API 未呼び出し。
  - 異常系: API 4xx/5xx/通信失敗時のエラー表示と遷移制御。

### 4. APIエラー応答のパース不備により、サーバー返却メッセージを正しく表示できない
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー編集.md ではサーバーサイドバリデーション結果を該当エラーメッセージとして表示する仕様。
  - 実装: frontend/src/pages/users/UserEdit.jsx の登録/更新処理で `const errorData = response.json();` としており await されないため `errorData.message` が参照できず、詳細エラーが欠落する。
- 指摘内容:
  - 重複チェック(USR02001)等の具体メッセージが表示されず、利用者が原因特定できない。
- 期待されるテスト:
  - POST/PUT が業務エラー(JSONメッセージあり)を返した場合、返却メッセージが AlertMessage に表示されること。

### 5. メッセージID運用が設計と分離しており、文言統一・保守性リスクが高い
- 優先度: Middle
- 種別: 設計確認事項
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー編集.md と spec/基本設計/機能設計/900.メッセージ/メッセージ定義.md では COM01004/COM01006/COM01008/COM01009/COM01010, COM02001等のメッセージID準拠で定義。
  - 実装: frontend/src/pages/users/UserEdit.jsx は文言をハードコードしており、frontend/src/constants/messageJP.ts の定義を参照していない。
- 指摘内容:
  - 設計で定義されたメッセージ体系とのトレーサビリティが弱く、文言差異や多言語対応時の不整合が発生しやすい。
- 期待されるテスト:
  - 主要イベント（登録確認、更新確認、戻る確認、完了、取得失敗）でメッセージIDに紐づく表示文言が選択されること。

### 6. テナントIDを固定値で送信しており、利用者コンテキストと乖離する可能性
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー編集.md では編集対象は指定ユーザーIDに基づく取得/更新であり、固定テナント利用は明示されていない。
  - 実装: frontend/src/pages/users/UserEdit.jsx の `fetchUserData` クエリで `tenantId` を固定文字列で指定している。
- 指摘内容:
  - 環境差異・ログインユーザー所属テナントと不一致時に誤取得/取得失敗を招くリスクがある。
- 期待されるテスト:
  - 利用者コンテキスト別テナントでの取得 API 呼び出し値が正しいこと。

### 7. ローディング表示が無効化され、通信中の多重操作抑止・待機状態可視化が不十分
- 優先度: Low
- 種別: 実装不備
- 対象: frontend/src/pages/users/UserEdit.jsx
- 根拠:
  - 設計書: spec/レイアウトサンプル/ユーザー管理/ユーザー編集.html では操作中の状態遷移を想定した UI 構成（ボタンイベント中心）であり、実装側は LoadingModal コンポーネントを備える。
  - 実装: frontend/src/pages/users/UserEdit.jsx で `LoadingModal` は import 済みだが描画はコメントアウトされている。
- 指摘内容:
  - 通信中の処理待ちが利用者に伝わりづらく、連打等の操作誘発リスクが残る。
- 期待されるテスト:
  - API通信開始時にローディング表示が出ること、終了時に解除されること。

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足
  - 新規登録成功時に完了メッセージ表示後、ユーザー検索画面へ遷移する確認が未整備。
  - 編集更新成功時に完了メッセージ表示後、ユーザー検索画面へ遷移する確認が未整備。
- 入力値バリエーション不足
  - ログインIDの未入力、全角混在、記号混在、空白のみ入力の検証が未整備。
  - メールアドレスの形式不正パターン（@欠落、ドメイン欠落、空白含む）の検証が未整備。
- 境界値不足
  - ログインID/ユーザー名/ユーザー名かなの100文字ちょうど、101文字の境界確認が未整備。
  - メールアドレス2048文字ちょうど、2049文字の境界確認が未整備。
- 分岐条件不足
  - 新規モード/編集モード表示切替（タイトル、ボタン表示）の確認が未整備。
  - 確認ダイアログのOK/キャンセル分岐、戻る時の変更あり/なし分岐の確認が未整備。
- データ入出力不足
  - 編集モード初期表示で取得データが各入力欄へ正しく反映される確認が未整備。
  - PUT/POST送信時のリクエストペイロード（userId, tenantId, times含む）の確認が未整備。
- 非更新確認不足
  - バリデーションNG時、APIが呼び出されないことの確認が未整備。
  - 確認ダイアログキャンセル時、APIが呼び出されないことの確認が未整備。
- 異常系不足
  - GET失敗時（対象データなし、通信失敗）にエラー表示と遷移制御が仕様どおりである確認が未整備。
  - POST/PUT失敗時（重複エラー、サーバー異常）のメッセージ表示と画面状態維持の確認が未整備。

## 総評
High 指摘として、戻る時の変更検知不備、編集初期取得失敗時の遷移不備、およびフロントエンドテスト未整備が品質リスクの中心です。
特に設計書で明示された非更新確認とエラー時導線を満たしていないため、仕様準拠性に課題があります。
まずは実装不備の修正と並行して、spec/050.テスト/テスト観点.md に沿った最小テストセットを優先整備すべきです。

## 残留リスク・確認できなかった範囲
- ユーザー編集の詳細設計書（spec/詳細設計）に相当する明示資料は確認できず、APIエラーマッピング（COM01009/COM01010の返却条件）を画面側でどこまで厳密に判定すべきかは追加確認が必要。
- フロントエンド権限制御（表示制御/遷移ガード）に関する設計記載が対象資料内で確認できず、未実装が仕様逸脱かどうかは確定できない。

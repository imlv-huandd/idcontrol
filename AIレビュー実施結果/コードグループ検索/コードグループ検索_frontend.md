# コードグループ検索 レビュー結果

## 指摘事項

### 1. 新規登録ボタンの権限制御が未実装

- 優先度: `High`
- 種別: `実装不備`
- 対象: `CodeGroupSearch.jsx`
- 根拠:
  - 設計書: `spec/基本設計/機能設計/100.コード定義/コードグループ検索.md` 検索条件エリア項目定義 No.5「新規登録ボタン：ログインユーザーがテナント管理者の場合のみ表示」
  - 実装: `isTenantAdmin` state が `false` で初期化されているが、権限取得APIの呼び出しが一切なく、`isTenantAdmin` が常に `false` のまま。ボタン表示の条件分岐も実装されておらず、全ユーザーに新規登録ボタンが表示される。
- 指摘内容:
  - `isTenantAdmin` の state 変数は宣言されているが、値をセットするロジックが存在しない。画面初期表示時に `getAuthMe` API等で権限を取得し、テナント管理者のみ新規登録ボタンを表示する実装が必要。
  - 他画面（`CodeGroupEdit.jsx`）では `fetch('/restapis/getAuthMe/...')` で `TENANT_ADMIN` を判定している。同等の実装が本画面には存在しない。
  - テナント管理者でないユーザーが新規登録画面に遷移できるため、認可不備にあたる。
- 期待されるテスト:
  - テナント管理者でログインした場合、新規登録ボタンが表示されること
  - 連携システム管理者でログインした場合、新規登録ボタンが非表示になること
  - 権限取得API呼び出しが画面初期表示時に行われること

### 2. 検索API呼び出しで認証なしの `fetch` を使用

- 優先度: `High`
- 種別: `実装不備`
- 対象: `CodeGroupSearch.jsx` `searchCodeGroups()`
- 根拠:
  - 設計書: `spec/基本設計/機能設計/100.コード定義/コードグループ検索.md` 検索ボタン押下「ログインユーザーの権限に応じて検索対象を制限する」（要認証）
  - 実装: `searchCodeGroups()` 内で `fetch(...)` を使用。`apiFetch` ではないため `credentials: "include"` が付与されず、401エラー時の自動リダイレクト処理も行われない。削除処理は `apiFetch` を使用しているのと対照的。
- 指摘内容:
  - セッション切れ状態で検索を実行した場合、401エラーが適切にハンドリングされず、ユーザーがログイン画面に誘導されない。
  - `apiFetch` に統一することで、認証必須エンドポイントへのアクセス一貫性が担保される。
- 期待されるテスト:
  - セッション切れ（401レスポンス）時にログイン画面へリダイレクトされること
  - 検索APIリクエストに認証情報（Cookie）が付与されること

### 3. 検索エラーが画面に表示されない

- 優先度: `High`
- 種別: `実装不備`
- 対象: `CodeGroupSearch.jsx` `loadCodeGroups()`
- 根拠:
  - 設計書: エラー発生時のユーザー通知は暗黙的に必要（設計書に明示的記載なし）
  - 実装: `loadCodeGroups()` の catch ブロックで `setError(err.message)` を呼んでいるが、JSX 内に `error` state を表示するコードが存在しない。`alert` state と `AlertMessage` コンポーネントは配置されているが、検索エラー時には `setAlert` が呼ばれず `setError` のみが呼ばれる。
- 指摘内容:
  - 検索APIがネットワークエラーやサーバーエラーで失敗した場合、ユーザーに何も通知されない。
  - `setError` を `setAlert({ type: 'error', ... })` に統一するか、JSX に `{error && <AlertMessage type="error" message={error} />}` を追加する必要がある。
- 期待されるテスト:
  - 検索APIが失敗した場合、エラーメッセージが画面に表示されること

---

### 4. 削除エラー時のメッセージ表示方式が設計と不一致

- 優先度: `Middle`
- 種別: `実装不備`
- 対象: `CodeGroupSearch.jsx` `handleDeleteConfirm()`
- 根拠:
  - 設計書: `spec/基本設計/機能設計/100.コード定義/コードグループ検索.md` 削除ボタン押下「サーバーサイドバリデーション：チェックエラーが発生した時点でメッセージをダイアログ表示し処理を中断」「削除ができなかった場合、全てロールバックしメッセージ(COM01010)をダイアログ表示し処理を終了」
  - 実装: `handleDeleteConfirm()` の catch ブロックで `setAlert({ type: 'error', message: err.message })` を呼んでおり、AlertMessage（アラートバー）として表示している。InforDialog は import および state 定義があるが未使用。
- 指摘内容:
  - 削除権限チェックエラー（COM01001）、属性項目使用チェックエラー（COD01001〜COD01003）、排他エラー（COM01010）はすべてダイアログ表示が設計で指定されているが、アラートバー表示になっている。
  - ダイアログと通知バーは UI 上のインパクトが異なり、ユーザーが気づかないリスクがある。
  - `InforDialog` の state（`inforDialog`）はセットされないため、実質デッドコードになっている。
- 期待されるテスト:
  - 削除権限なし（COM01001）のとき、ダイアログが表示されること
  - 組織属性項目使用中（COD01001）のとき、ダイアログが表示されること
  - 排他エラー（COM01010）のとき、ダイアログが表示されること

### 5. `handleDelete` の `useCallback` 依存配列に `codeGroupName` が含まれていない

- 優先度: `Middle`
- 種別: `実装不備`
- 対象: `CodeGroupSearch.jsx` `handleDelete`
- 根拠:
  - 設計書: `spec/基本設計/機能設計/100.コード定義/コードグループ検索.md` 削除ボタン押下「現在のページで検索を再実行し、一覧を更新する」
  - 実装: `handleDelete` の `useCallback` 依存配列は `[currentPage]` のみ。内部で `handleDeleteConfirm` をクロージャキャプチャしているが、`handleDeleteConfirm` は `useCallback` でラップされておらず毎レンダリングで再生成される。よって `handleDelete` が `currentPage` 変更前の古いレンダリングでメモ化されている場合、その時点の `handleDeleteConfirm`（= 古い `codeGroupName` をクロージャに持つ）が `onConfirm` として登録される。
  - `codeGroupName` を変更 → 削除ボタン押下 → 確認ダイアログの onConfirm が古い `codeGroupName` で再検索を実行する可能性がある。
- 指摘内容:
  - `handleDelete` の依存配列に `handleDeleteConfirm`（または `codeGroupName`）を追加するか、`handleDeleteConfirm` も `useCallback` でラップして依存関係を整理する必要がある。
- 期待されるテスト:
  - 検索条件を変更した後に削除を実行すると、最新の検索条件で一覧が再表示されること

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）

テストコードが未作成の前提で、以下の観点でテストが不足している。

### 正常系不足
- コードグループ名を入力して検索したとき、一致するコードグループが一覧表示されること
- コードグループ名を未入力（空欄）で検索したとき、全件が取得されること
- 削除ボタン押下後に確認ダイアログが表示され、確認後に削除が完了しメッセージ(COM01005)が表示されること
- 削除後、現在ページの一覧が再取得されて表示が更新されること
- 編集ボタン押下でコードグループ編集画面（編集モード）に遷移すること
- テナント管理者で新規登録ボタンが表示され、押下でコードグループ編集画面（新規モード）に遷移すること

### 入力値バリエーション不足
- コードグループ名に部分一致する文字列で検索したとき、部分一致するコードグループのみ返されること
- コードグループ名に全角・半角・記号を含む文字列で検索できること
- 連携システム管理者でログインした場合、対象システムに紐づくコードグループのみ表示されること
- テナント管理者でログインした場合、全コードグループが表示されること

### 境界値不足
- 検索結果がちょうど PAGE_SIZE（8件）のとき、ページネーションが1ページのみ表示されること
- 検索結果が PAGE_SIZE+1（9件）のとき、2ページ表示になること
- コードが5件ちょうどのとき、カンマ区切りで5件すべて表示されること
- コードが6件以上のとき、先頭5件 + `...（X件）` の形式で表示されること
- 検索結果が0件のとき、メッセージ(COM01003)が表示されること

### 分岐条件不足
- テナント管理者でない（連携システム管理者・一般ユーザー）場合、新規登録ボタンが非表示になること
- 削除確認ダイアログでキャンセルした場合、削除が実行されないこと
- 削除後に現在ページのデータが0件になった場合、前のページに自動的に戻ること
- 削除後に現在ページにデータが残っている場合、同ページのままで一覧が更新されること
- ローディング中にボタンが非活性になること

### データ入出力不足
- 削除実行後、対象コードグループが一覧から消えていること
- 検索後に一覧表示されるコードグループ名・コードが API レスポンスの値と一致すること

### 非更新確認不足
- クリアボタン押下後、検索結果エリアが非表示になること
- クリアボタン押下後、コードグループ名入力欄が空欄になること
- 削除キャンセル後、一覧が変更されないこと

### 異常系不足
- 検索API失敗時（ネットワークエラー等）にエラーメッセージが表示されること（※現状実装バグにより非表示 → #3 の修正後にテスト可能）
- 削除API失敗時にエラーメッセージが表示されること
- 削除権限なし（COM01001）のとき、ダイアログにエラーメッセージが表示されること
- 組織属性項目使用中（COD01001）のとき、ダイアログにエラーメッセージが表示されること
- 役職属性項目使用中（COD01002）のとき、ダイアログにエラーメッセージが表示されること
- 就業者属性項目使用中（COD01003）のとき、ダイアログにエラーメッセージが表示されること
- 排他エラー（COM01010）のとき、ダイアログにエラーメッセージが表示されること
- セッション切れ（401）時にログイン画面へリダイレクトされること（※検索APIの apiFetch 対応後に有効）

---

## 総評

High 指摘が3件あり、いずれも現状でマージ不可レベル。特に「新規登録ボタンの権限制御未実装」は認可不備であり、テナント管理者以外のユーザーが新規登録画面に遷移できるセキュリティリスクがある。「検索APIの認証なし fetch」は401ハンドリング欠如による UX 劣化と認証一貫性欠如の問題。「検索エラーの非表示」はユーザーにサイレント障害をもたらす。Middle の削除エラーのダイアログ/アラート不一致は設計逸脱であり修正推奨。テストコードは全観点で未作成のため、正常系・権限制御・異常系を中心に幅広い観点でのテスト実装が必要。

---

## 残留リスク・確認できなかった範囲

- 検索APIのサーバーサイド権限絞り込み（テナント管理者/連携システム管理者による取得範囲制限）はバックエンド（`functions/codegroups/searchCodeGroups/app.py`）で実装されているかどうかをフロントエンドレビューの範囲では確認できなかった。バックエンドのレビューで別途確認が必要。
- `getAuthMe` API の呼び出しタイミング（初期表示時 vs hooks 経由）については、`CodeGroupEdit.jsx` の `fetch` パターンと `GroupSearch.jsx` の `useAuth()` パターンが混在しており、プロジェクト内の統一方針が不明。採用すべきパターンを確認のうえ実装すること。
- ページネーション設計書（`ページネーション.md`）ではデフォルト20件/ページと定義されているが、本画面では `PAGE_SIZE = 8` を使用している。意図的な画面固有設定か確認が必要。

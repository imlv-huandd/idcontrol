# ユーザー検索 レビュー結果

## 指摘事項

### 1. テナント越境データ参照の防止観点が不足
- 優先度: High
- 種別: 観点不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md の「検索ボタン押下」ではログインユーザー文脈でユーザー検索を行う前提。項目表No.4は全件検索時のテナント絞り込みのみ確認しており、条件指定時の越境抑止が未確認。
  - 実装: 実装コード未提示のため、検索APIでのテナント条件強制付与有無を確認不可。
- 指摘内容:
  - 全条件未入力時のテナント絞り込みは確認されているが、ログインIDやメールアドレス等で他テナントの実在値を入力した場合に結果へ混入しないことの検証が不足している。
  - マルチテナント境界の漏れは情報漏えいに直結するため、リリース前に追加が必要。
- 期待されるテスト:
  - 他テナントにのみ存在する login_id/user_name/mail_address を入力して検索し、0件または自テナント結果のみとなること。
  - 複合条件時（自テナント条件 + 他テナント条件）でも他テナントデータが返らないこと。

### 2. 依存先異常時の検索失敗ハンドリングが不足
- 優先度: High
- 種別: 項目不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md のイベント処理は検索/削除でサーバー連携を伴うが、項目表では検索処理の異常系（サーバーエラー、タイムアウト、通信断）が未定義。
  - 実装: 実装コード未提示のため、例外時のメッセージ制御・画面状態維持ロジックの実装有無を確認不可。
- 指摘内容:
  - 検索異常時のユーザー通知、既存表示の維持/クリア、再試行可否など運用上重要な挙動がテストされていない。
  - 依存先異常の未検証は、障害時に画面フリーズや誤表示を見逃すリスクが高い。
- 期待されるテスト:
  - 検索API 500/503 応答時にエラーメッセージが表示され、検索結果表示状態が仕様どおり維持または非表示になること。
  - タイムアウト時のメッセージと操作継続性（再検索可能）を確認すること。
  - エラー時にDB更新が発生しないこと（非更新確認）。

### 3. 検索条件入力の境界値・不正値観点が不足
- 優先度: Middle
- 種別: 観点不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md の項目定義に4つのテキスト入力項目があるが、項目表は部分一致の正常系中心で、入力制約の検証が不足。
  - 実装: 実装コード未提示のため、フロント/サーバー双方の入力チェック実装（長さ制限、制御文字、前後空白処理）確認不可。
- 指摘内容:
  - 文字数上限、空白のみ入力、前後空白付き入力、特殊文字入力時の挙動が未確認で、検索漏れや誤ヒットの温床になり得る。
- 期待されるテスト:
  - 各入力項目の最小/最大文字数、上限超過、空白のみ入力のケース。
  - 前後空白を含む入力時のトリム有無に応じた検索結果。
  - 記号やワイルドカード相当文字入力時に想定外の広範囲ヒットやエラーが起きないこと。

### 4. 0件時・エラー時のページネーション状態確認が不足
- 優先度: Middle
- 種別: 記載不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md の「画面初期表示」「検索ボタン押下」では結果エリア/ページング表示制御が明記。
  - 実装: 実装コード未提示のため、0件時にページングが非表示化される実装有無を確認不可。
- 指摘内容:
  - No.12は0件時メッセージ確認のみで、ページングエリア非表示や表示件数ラベルの整合性確認が不足している。
  - 異常応答時のページング状態（現在ページ維持/リセット）も未定義。
- 期待されるテスト:
  - 0件時にページングエリアが非表示であること。
  - 0件時の表示範囲ラベル未表示または仕様どおりの表示であること。
  - 検索異常時にページ番号や件数表示が不整合にならないこと。

### 5. 1ケースに複数観点を含み、原因切り分けが難しい項目がある
- 優先度: Middle
- 種別: 記載不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md はイベント単位で仕様を分離している。
  - 実装: 実装コード未提示のため、失敗時の分岐箇所を直接確認できず、テスト項目粒度の重要性が高い。
- 指摘内容:
  - 例としてNo.4（テナント絞り込み + ソート順）、No.31（再検索実行 + 表示更新）、No.43/44（複数ボタン状態同時確認）は、1ケースで複数観点を同時検証している。
  - 失敗時に原因を一意に特定しづらく、保守性が低下する。
- 期待されるテスト:
  - 複合ケースを分割し、1ケース1観点で期待結果を独立させること。
  - 例: No.4を「テナント絞り込み確認」と「メール昇順ソート確認」に分離すること。

### 6. 一部項目の種別ラベルと期待結果粒度に不整合がある
- 優先度: Low
- 種別: 記載不足
- 対象: 単体テスト仕様書 ― ユーザー検索画面
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md の削除仕様では関連テーブル削除は更新処理。
  - 実装: 実装コード未提示のため、更新有無判定は項目表記述に依存。
- 指摘内容:
  - No.54/55は「非更新確認」となっているが、実際は関連テーブル削除の更新確認であり、分類が不一致。
  - 「エラーが発生しないこと」などの抽象表現があり、判定基準が曖昧。
- 期待されるテスト:
  - 種別を「データ入出力」または「正常系」に統一し、期待結果を件数・対象キー・副作用有無まで具体化すること。

## 総評
- 検索・削除の主要正常系は広くカバーされている一方、テナント境界と依存先異常という高リスク観点の欠落がある。
- 特にデータ漏えい防止（越境検索防止）と障害時挙動（検索API異常）は High として優先的に補完が必要。
- 次点で、入力境界値とケース分割を整備することで、不具合の早期検出と原因切り分け性が向上する。

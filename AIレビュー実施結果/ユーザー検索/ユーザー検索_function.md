# ユーザー検索 レビュー結果

## 指摘事項

### 1. deleteUser API が詳細設計の入出力契約と不一致（userId の受け取り位置・times 未実装・タイムスタンプ条件削除未実装）
- 優先度: High
- 種別: 実装不備
- 対象: functions/users/deleteUser/app.py
- 根拠:
  - 設計書: spec/詳細設計/openapi/paths/users.yaml で deleteUser は userId を path で受け取り、times 必須（L94, L99）。spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md で削除条件に「ユーザーID + タイムスタンプ」（L105-109）。
  - 実装: functions/users/deleteUser/app.py で userId を body から取得（L44付近）、times は TODO で未使用（L63付近コメント）、delete_user 呼び出し時にタイムスタンプ条件なし（L59）。
- 指摘内容:
  - API 契約と実装が一致しておらず、クライアントとの接続不整合と同時更新競合の検知漏れが発生する。
  - 設計で要求される楽観ロック条件が欠落し、検索後に更新されたデータでも削除できるリスクがある。
- 期待されるテスト:
  - OpenAPI 契約どおり path userId + required times での正常系。
  - times 欠落/不正形式時の異常系。
  - タイムスタンプ不一致時に削除しない（非更新）ことの検証。

### 2. 削除チェック（USR01001: ログインユーザー自身の削除禁止）が未実装
- 優先度: High
- 種別: 実装不備
- 対象: functions/users/deleteUser/app.py
- 根拠:
  - 設計書: spec/基本設計/機能設計/030.ユーザー管理/ユーザー検索.md のバリデーション定義で「削除対象のユーザーIDがログインユーザーのユーザーIDと異なること」（L152相当）。
  - 実装: functions/users/deleteUser/app.py は login_user_id を取得しているが、user_id との比較チェックがない（L33, L44-52, L55以降）。
- 指摘内容:
  - 設計必須のサーバーサイド削除チェックが欠落しており、自己削除を許容する可能性がある。
- 期待されるテスト:
  - login_user_id == user_id のときに業務エラーを返し、削除処理へ進まないこと。

### 3. deleteUser の高リスク分岐を検証する単体テストが不足
- 優先度: High
- 種別: テスト不足
- 対象: tests/functions/users/test_deleteUser.py
- 根拠:
  - 設計書: spec/050.テスト/テスト観点.md の単体テスト観点（分岐条件、非更新確認、異常系）。ユーザー検索.md の削除仕様（times 必須、削除チェック、複数テーブル削除、ロールバック）。
  - 実装: tests/functions/users/test_deleteUser.py は 204/400/401/403/500 の基本系はあるが、path userId・times 必須・自己削除禁止・タイムスタンプ不一致・部分失敗時ロールバックの検証がない（L15-116）。
- 指摘内容:
  - 仕様上重要な削除分岐が未検証で、実装不備があっても検知できない。
  - モック中心のため、関連テーブル削除途中失敗時の整合性破綻を見逃す構成になっている。
- 期待されるテスト:
  - path/body 入力差異の検証。
  - times 必須/形式エラー。
  - 自己削除禁止。
  - 関連テーブル削除途中失敗時のロールバック（DB副作用なし）。

### 6. searchUsers のテストが仕様観点を十分に網羅していない
- 優先度: Middle
- 種別: テスト不足
- 対象: tests/functions/users/test_searchUsers.py
- 根拠:
  - 設計書: spec/050.テスト/テスト観点.md の入力値バリエーション、境界値、分岐条件、データ入出力。
  - 実装: tests/functions/users/test_searchUsers.py は基本成功・0件・デフォルトページング・例外はあるが、4条件同時指定、ソート順、page/pageSize 異常値の検証がない（L16-135）。
- 指摘内容:
  - 検索条件組み合わせや境界入力での不具合が未検知となる。
- 期待されるテスト:
  - 4条件同時指定、全空指定、部分一致の境界ケース。
  - page/pageSize の 0、負数、非数値、大きな値。
  - 並び順（mail_address 昇順）の検証。

### 7. ユーザー未検出時レスポンスの妥当性は設計確認が必要（500 固定）
- 優先度: Low
- 種別: 設計確認事項
- 対象: functions/users/deleteUser/app.py
- 根拠:
  - 設計書: ユーザー検索.md では削除失敗時に COM01010 を表示とあるが、未検出時の HTTP ステータス区分は明確化されていない。
  - 実装: functions/users/deleteUser/app.py は未検出時 Exception を投げ、最終的に 500/COM01010 を返す（L58-60, L111-112）。
- 指摘内容:
  - 仕様として「未検出は業務エラー（4xx）かシステムエラー（5xx）か」の定義が曖昧なため、API 契約を明確化すべき。
- 期待されるテスト:
  - 仕様確定後、未検出時のステータス・エラーコード・メッセージを固定する契約テスト。

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足
  - deleteUser の path userId + times を満たす契約どおりの正常系が未検証。
- 入力値バリエーション不足
  - searchUsers の4条件組み合わせ、全空入力、deleteUser の path/body 差異が未検証。
- 境界値不足
  - searchUsers の page/pageSize の 0、負数、非数値、大値が未検証。
- 分岐条件不足
  - 自己削除禁止（USR01001）、times 不一致時非削除、関連テーブル有無分岐が未検証。
- データ入出力不足
  - 検索結果の mail_address 昇順、delete 後関連テーブル削除結果、操作ログ内容の妥当性検証が弱い。
- 非更新確認不足
  - タイムスタンプ不一致時、削除途中失敗時にデータが更新されないことの確認がない。
- 異常系不足
  - deleteUser の times 欠落/不正、自己削除、削除途中失敗時ロールバック異常系が不足。

## 総評
High 指摘は、削除API契約不一致と削除チェック欠落、ならびにそれを検知できないテスト不足に集中している。
このままではクライアント連携不整合と誤削除リスクが残り、リリース判定上の重大リスクとなる。
優先順位は、1) deleteUser の契約準拠化と削除チェック実装、2) ロールバック含むテスト補強、3) 検索ソート順是正の順が妥当。

- 実DB を用いたトランザクション検証（削除途中失敗時の整合性）は本レビュー範囲外のため未確認。

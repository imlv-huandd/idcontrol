# グループ権限編集 レビュー結果

## 指摘事項

### 1. 上位権限選択時にダウンロード権限が自動付与されない
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「更新ボタン押下」で、テナント管理者、マスターデータ管理者、いずれかの連携システム管理者権限を持つ場合は、ダウンロード権限をチェック状態に関わらず自動追加すると定義されている。
  - 実装: GroupPermissionEdit.jsx の更新処理では、downloadPermission が true の場合にしか DOWNLOAD を permissions に追加しておらず、上位権限からの自動付与条件を判定していない。
- 指摘内容:
  - テナント管理者、マスターデータ管理者、連携システム管理者を選択しても、ダウンロードチェックがオフなら DOWNLOAD が送信されない。保存される権限セットが設計と不一致になり、画面の注意文とも矛盾する。
- 期待されるテスト:
  - テナント管理者のみ選択し、ダウンロード未選択でも更新 payload に DOWNLOAD が含まれること。
  - マスターデータ管理者のみ選択し、ダウンロード未選択でも更新 payload に DOWNLOAD が含まれること。
  - 連携システム管理者を1件以上選択した場合、ダウンロード未選択でも更新 payload に DOWNLOAD が含まれること。
  - 上位権限がない場合のみ、DOWNLOAD はチェック状態に応じて送信されること。

### 2. 連携システム権限の表示・選択範囲が設計より広く、権限外の設定操作を試行できる
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「画面初期表示」「権限設定可能チェック」で、ログインユーザーが持つ権限以下のみ設定可能、かつ連携システム関連権限は該当する連携システムの権限を持つ場合のみ設定可能と定義されている。
  - 実装: GroupPermissionEdit.jsx では、連携システム操作者セクションの表示条件に RELATION_SYSTEM_USER を含めている。また、listRelationSystems で取得した全システムをそのままチェックボックス化しており、ログインユーザーが権限を持たない systemId も選択可能になっている。
- 指摘内容:
  - 連携システム操作者権限しか持たないユーザーにも権限設定 UI が表示されるうえ、連携システム管理者は自分が管理していないシステムにも権限を付与できる見た目になる。サーバー側の AUT02002 で拒否される前提でも、フロントエンドの権限制御として設計逸脱であり、誤操作や不要な権限付与試行を招く。
- 期待されるテスト:
  - RELATION_SYSTEM_USER のみを持つログインユーザーでは、連携システム管理者／操作者セクションが表示されないこと。
  - RELATION_SYSTEM_ADMIN を持つログインユーザーでは、自身が権限を持つ systemId のみ選択肢が表示されること。
  - MASTER_DATA_ADMIN を持つログインユーザーでは、マスターデータ管理者、閲覧者、ダウンロード権限のみ表示されること。
  - 権限外の連携システムをフロントエンドから選択できないこと。

### 3. 楽観的ロック用の times を sessionStorage に依存しており、再表示や直接遷移で更新できなくなる
- 優先度: High
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「更新ボタン押下」で、更新条件に取得時のタイムスタンプを含めることが明記されている。spec/詳細設計/openapi/components/groups.yaml でも GroupPermissionsUpdateRequest の times は必須である。
  - 実装: GroupPermissionEdit.jsx は初期表示時に sessionStorage から group_authority_times を読み出して state に保存し、その後 sessionStorage から削除している。getGroup のレスポンスから times を保持する実装はなく、sessionStorage が欠落した場合でも更新処理を継続する。
- 指摘内容:
  - 画面再読み込み、直接 URL 遷移、別タブ遷移などで sessionStorage が空の状態になると、更新時に times が null のまま送信される。設計上必須の楽観的ロック条件を満たせず、更新不能または誤ったエラー表示につながる。
- 期待されるテスト:
  - 画面初期表示 API から取得した times を保持したまま更新できること。
  - 編集画面を再読み込みした場合でも更新に必要な times を喪失しないこと。
  - times が古い場合は COM01010 が表示されること。
  - times が取得できない場合は更新 API を呼ばず、利用者に再読込を促すこと。

### 4. 連携システム一覧と所属ユーザー一覧の表示順が設計で定義された順序で保証されていない
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「権限設定エリア」で、連携システム管理者／操作者セクションの表示順はシステム名の昇順と定義されている。同ファイルの備考では、所属ユーザー名の表示順序はメールアドレスの昇順と定義されている。
  - 実装: GroupPermissionEdit.jsx では relationSystems を API レスポンスの順のまま state に格納し、members も受信した配列をそのまま map で描画している。フロントエンド側でのソート処理は存在しない。
- 指摘内容:
  - API が設計どおりの順序で返す保証がコード上にないため、表示順が不定になる。設計上、画面の見え方として規定された順序をフロントエンドが担保できていない。
- 期待されるテスト:
  - 連携システム一覧が未ソートで返ってきた場合でも、画面上では systemName 昇順で表示されること。
  - 所属ユーザー一覧が未ソートで返ってきた場合でも、画面上では mailAddress 昇順で表示されること。
  - 所属ユーザーが 0 件の場合に「（未設定）」が表示されること。

### 5. 初期表示時の障害をすべて同じ扱いで強制遷移しており、障害内容に応じた復帰動線になっていない
- 優先度: Middle
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「画面初期表示」では、グループが存在しない場合に COM01009 を表示して検索画面へ遷移すると定義されている。一方で、認証 API や連携システム一覧取得失敗時の強制遷移までは定義されていない。
  - 実装: GroupPermissionEdit.jsx の初期表示処理は、getAuthMe、getGroup、listRelationSystems のいずれかが失敗しても catch で一律に alert を表示し、3 秒後に /group-permissions へ遷移している。
- 指摘内容:
  - 一時的な通信障害や連携システム一覧取得失敗でも、対象データなしと同様に画面から追い出される。再試行や状況把握の機会がなく、障害切り分けもしづらい。仕様で明示された COM01009 のケースと、それ以外の外部障害が区別されていない。
- 期待されるテスト:
  - getGroup が 404 相当で失敗した場合のみ COM01009 を表示して検索画面へ遷移すること。
  - getAuthMe または listRelationSystems が失敗した場合、画面遷移せずエラーメッセージを表示して再試行可能な状態を保つこと。
  - updateGroupPermissions 失敗時は現在画面に留まり、入力状態が失われないこと。

### 6. フロントエンド単体テストが未作成で、仕様上重要な分岐がまったく担保されていない
- 優先度: Middle
- 種別: テスト不足
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/050.テスト/テスト観点.md の単体テスト観点では、正常系、入力値バリエーション、境界値、分岐条件、データ入出力、非更新確認、異常系を対象機能に応じて網羅することが求められている。
  - 実装: frontend/src/pages/permissions 配下および関連箇所に、GroupPermissionEdit を対象としたテストコードは存在しない。権限制御、更新 payload、通信失敗、確認ダイアログの挙動を検証する仕組みが未整備である。
- 指摘内容:
  - 本機能は表示制御、権限選択、楽観的ロック、複数 API 連携、確認ダイアログを含む分岐の多い画面だが、現状は回帰を検知する自動テストがない。今回確認した実装不備もテスト不在のままでは再発しやすい。
- 期待されるテスト:
  - 役割別表示制御、AUT02001、更新確認 COM01006、キャンセル確認 COM01008、COM01009、COM01010、更新成功 COM01004 を含む画面テストを作成すること。
  - 更新 payload に含まれる authority と relationSystemId の組み立てを検証すること。
  - 通信失敗時に画面遷移や alert 表示が設計どおりであることを検証すること。

### 7. 現在のグループ権限表示の書式が設計記載と一致していない
- 優先度: Low
- 種別: 実装不備
- 対象: frontend/src/pages/permissions/GroupPermissionEdit.jsx
- 根拠:
  - 設計書: spec/基本設計/機能設計/050.権限管理/グループ権限編集.md の「グループ情報エリア」では、連携システム管理者、連携システム操作者権限は末尾に「（連携システム名）」を付与して表示すると定義されている。
  - 実装: GroupPermissionEdit.jsx の現在権限表示は、権限名の後にコロンを付け、連携システム名をグレー文字で並べている。括弧付きの表記にはなっていない。
- 指摘内容:
  - 権限表示の意味自体は伝わるが、設計で規定された表示書式と一致していない。表示確認を仕様ベースで進める場合に差分として残る。
- 期待されるテスト:
  - RELATION_SYSTEM_ADMIN と RELATION_SYSTEM_USER の表示が「権限名（連携システム名）」形式で描画されること。
  - システム名がないデータでは権限名のみ表示されること。

## テスト不足の整理（spec/050.テスト/テスト観点.md 準拠）
- 正常系不足: 初期表示成功、既存権限のチェック反映、更新成功後の COM01004 表示と一覧画面遷移、キャンセル時の画面遷移を確認するテストがない。
- 入力値バリエーション不足: テナント管理者、マスターデータ管理者、連携システム管理者、連携システム操作者、閲覧者、ダウンロードの単独選択と組み合わせ選択を検証するテストがない。
- 境界値不足: 連携システム 0 件、所属ユーザー 0 件、連携システム複数件、権限未選択、times 欠落・不一致といった境界条件を確認するテストがない。
- 分岐条件不足: ログインユーザー権限ごとの表示制御、RELATION_SYSTEM_USER 単独時の非表示、上位権限選択時の DOWNLOAD 自動付与など、仕様分岐を確認するテストがない。
- データ入出力不足: updateGroupPermissions に送る authority 一覧、relationSystemId、times、更新 API 成功・失敗レスポンスの取り扱いを確認するテストがない。
- 非更新確認不足: COM01008 でキャンセルした場合に更新 API を呼ばないこと、AUT02001 エラー時に更新 API を呼ばないこと、他グループや他権限に副作用がないことを確認するテストがない。
- 異常系不足: getGroup の対象データなし、getAuthMe 失敗、listRelationSystems 失敗、updateGroupPermissions の AUT02002、COM01010、ネットワーク障害時の画面挙動を確認するテストがない。

## 総評
- High 指摘は、権限制御の逸脱、DOWNLOAD 自動付与漏れ、times の保持方法という、画面の仕様充足と更新成功可否を直接左右する項目です。
- 現状はサーバー側バリデーションに依存して破綻を回避している箇所があり、フロントエンド単体では設計どおりの入力制御を担保できていません。
- 修正優先度は、まず権限付与ロジックと times 取得方法、その後に表示順・障害時遷移・テスト整備の順が妥当です。

## 残留リスク・確認できなかった範囲
- 項目定義表では「マスターデータ管理者」の表示条件が「テナント管理者または連携システム管理者」と読める一方、イベント詳細では「テナント管理者またはマスターデータ管理者」と記載されており、設計書内に不整合があります。実装はイベント詳細側の解釈に近いため、正とする記載の確認が必要です。
- auth の OpenAPI からは authorities が文字列配列であることは確認できましたが、連携システム単位の権限範囲をフロントエンドがどの API で取得すべきかは明確に確認できませんでした。設計どおりの systemId 単位制御をフロントで担保する責務分担は要確認です。
- フロントエンドのテストコードは未作成前提で確認しており、実際のバックエンド実装や API レスポンス順序保証まではこのレビューでは検証していません。
